## 1. 結論（先出し）

**対応不要（既に解決済み）。** GitHub から通知された約18件の連続失敗は、
デプロイCI（GitHub Actions → SSH → PM2）を**新規に立ち上げた 2026-05-25〜05-26 の
初期セットアップ期間に集中した一過性のもの**であり、
**`c13ac0f`（2026-05-26 07:59）の修正で収束済み**と判断できる。

現行の `deploy.yml` 構成は妥当で、失敗が継続する要因は読み取れない。

この修正系列（SSH認証 → ビルド依存 → 所有権 → git競合）は、
通知された **「Attempt #2〜#11 を含む約18件の連続失敗（〜5/26）」と時系列・件数が一致する。**
すなわち失敗群は、CI を試行錯誤で立ち上げる過程そのものだった。

### 2-2. 失敗が「収束した」根拠

- `deploy.yml` への変更は `c13ac0f`（05-26 07:59）を**最後に一度も発生していない**。
- 一方、`master` への push は **05-27 以降も40件以上**継続している
  （例: 05-27, 05-29, 06-01, 06-02, 06-03, 06-13, 06-14, 06-16, 06-21, 06-22）。
  最新 HEAD は `91a440c`（2026-06-22）。
- ワークフローは `on: push: branches: [master]` なので、これら全 push でデプロイが起動するはず。
  **もし失敗が継続していれば、5/26 以降も大量の失敗通知が届いていたはずだが、通知は 5/26 で途絶えている。**
  → 5/26 の修正以降、デプロイは成功（グリーン）で安定していると判断できる。
- 加えて [docs/deployment.md](./deployment.md) と CLAUDE.md のデプロイ手順には、
  この修正内容（`git fetch` + `reset --hard` / `npm install --omit=dev`）が
  **正規手順として明文化済み**であり、解決が定着していることを裏付ける。

## 3. 連続失敗の原因仮説（当時）

最終的に動いている現行 `deploy.yml` から逆算すると、初期失敗の原因は以下が順に潰されたものと読み取れる。

1. **SSH / サービスアカウント認証の不整備**
   `a67a512` で「auth failure」診断用に `debug: true` を追加。
   秘密鍵の登録漏れ・改行欠落、`GCP_SSH_HOST/USER/PORT` 等の Secrets 未設定、
   VM 側 `authorized_keys` 未登録、ファイアウォールで GitHub Actions レンジからの TCP:22 不許可、
   のいずれか（または複数）が初期の失敗要因の筆頭候補。

2. **ビルド依存の欠落**
   `418d8b9` で対応。`npm ci`/`--omit=dev` 系だと `tsc`（devDependency）が無く
   `npm run build` が失敗するため、devDependencies を入れてからビルド→`npm prune --omit=dev` の順に修正。

3. **リポジトリ所有権の不整合**
   `55b4aff` で対応。root 所有ファイル混在で `git`/`npm` が権限エラー。
   現行は `sudo chown -R "$(whoami)" ~/NumberTales-MisskeyAIBot/` で吸収。

4. **`git pull` のローカル変更コンフリクト**
   `c13ac0f` で対応。VM 上の `dist/` 等の生成物で `git pull` が競合・失敗。
   `git fetch origin master` + `git reset --hard origin/master` に変更して解消。

これらはいずれも**新規CIブートストラップ時の典型的な詰まり**であり、構造的な欠陥ではない。

## 4. 現行構成の評価と（任意の）改善余地

現行 `deploy.yml` は妥当。緊急の修正は不要。将来の堅牢化として検討余地があるのは以下（任意・低優先）。

- **`npm install` → `npm ci` 化**: 再現性向上。ただし `tsc` がビルドに必要なため
  `--omit=dev` は付けず、ビルド後に `npm prune --omit=dev` する現行方針は維持する。
- **`debug: true` の常時有効**: 認証情報そのものは出力されないが、安定稼働後はノイズになるため
  問題切り分け時のみ有効化する運用でもよい。
- **失敗時の通知制御**: 立ち上げ期の大量失敗通知が負担なら、`concurrency` 設定で
  古い実行をキャンセルする、あるいは通知設定を調整する。
- **デプロイ対象の限定**: ドキュメントのみの push（`docs/**`, `_ideas/**` 等）では
  再デプロイ不要なケースが多いため、`paths-ignore` でビルド不要な変更を除外すると無駄な実行を減らせる。
