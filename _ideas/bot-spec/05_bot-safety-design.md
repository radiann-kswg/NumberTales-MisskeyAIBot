## 概要

Fediverseで実際に発生したBotトラブルの事例と、藍(Ai)をはじめとする成熟したBotの設計思想から
学んだ知見を、ナンバーテールズBotの設計原則として明文化する。

これらの原則は機能横断的に適用され、新規機能の追加時も必ず参照すること。

## 1. LTL汚染防止

### 背景にある事例

- MisskeyでRSS配信Botが2時間で700件以上の公開投稿を生成し、TLを埋め尽くしたインシデントがある
- おみくじBotが多ユーザーのリクエストで公開TLを占い結果で溢れさせた事例もある
- お一人様サーバのため外部LTLへの影響は小さいが、フォロイーのHTLを汚染するリスクは常に存在する

### 原則

| 投稿カテゴリ | 推奨公開範囲 | 理由 |
|------------|------------|------|
| 自発投稿（F-02） | `public` | フォロワー外への露出で新規フォロワー獲得 |
| メンション返信（通常） | `home` | フォロイーのHTLにのみ流す |
| 個人向け応答（占い・リマインド・誕生日） | `home` または `specified` | リクエストしたユーザーにのみ届ける |
| Poll投票ノート（F-06 週次担当） | `public` | 対話型コンテンツとして公開 |
| ゲーム中のやり取り | `home` | ゲームセッションをTLに流さない |

### 自発投稿の頻度管理

- スロット間の最短クールダウンをランダムで設定（機械的な定時投稿を避ける）
- 同日内の自発投稿がN件を超えた場合、次スロットをスキップする安全弁を設ける
- `RATE_LIMIT_GLOBAL_PER_HOUR` のグローバル上限が全機能に一律で適用される

## 2. 暴走防止

### 背景にある事例

タイムスタンプ処理のバグが原因で全記事が「新着」と誤判定され、
RSS配信Botが連続投稿を繰り返した事例（Misskey 2023年）。

### 原則

#### a) 種別ごとのレート制限（多層防御）

```
Layer 1: 機能単位の制限
  → F-10: 1ユーザー1日1回
  → F-12: スケジューラーは5分間隔チェック
  → F-02: クールダウン 1〜2時間

Layer 2: グローバル上限
  → RATE_LIMIT_GLOBAL_PER_HOUR = 10（デフォルト）
  → 上限超過時は次の時間帯までキュー

Layer 3: 重複防止
  → 処理済みノートIDをキャッシュ
  → 自分のノートへのリアクション/リプライは無視
```

#### b) スケジューラーの安全設計

```typescript
// F-12 リマインダースケジューラーの例
// 一度の実行で取り出す件数を上限設定
const MAX_PROCESS_PER_RUN = 5;
const dueReminders = db.prepare(
  "SELECT * FROM reminders WHERE status='pending' AND remind_at <= ? LIMIT ?"
).all(now, MAX_PROCESS_PER_RUN);
```

- 1回の実行で処理する件数に上限を設ける
- 大量のpendingが溜まっていても一度に送信しない

#### c) ドライランモード

新機能の初回デプロイ時は `DRY_RUN=true` 環境変数で実際の投稿をスキップして動作確認できるようにする（既存設計に準じて実装）。

## 3. ランダム値生成の原則

### 背景にある事例

おみくじBotでLLMにランダム結果を生成させたところ、
「大吉」ばかり出る偏りが生じ、ランダム性が担保されなかった事例。

### 原則

**LLMにランダム値を生成させない。乱数・抽選は必ずコード側で確定させてからLLMに渡す。**

```typescript
// ✅ 正しい
const pool = ANGEL_NUMBER_POOL;
const selected = weightedRandom(pool);  // コード側でランダム決定
const message = await llm.generate({
  prompt: `今日のエンジェルナンバーは${selected.number}です。キャラとして解釈文を生成してください。`
});

// ❌ 間違い
const message = await llm.generate({
  prompt: 'エンジェルナンバーをランダムに一つ選んで解釈してください'
  // LLMが偏ったランダム選択をする可能性がある
});
```

| 機能 | ランダム値の生成方法 |
|-----|------------------|
| F-10 エンジェルナンバー占い | `weightedRandom(ANGEL_NUMBER_POOL)` でコード側抽選 |
| F-06D 数字スロット | `Math.random()` で3桁生成 |
| F-06D ヒット＆ブロウ | `crypto.randomInt()` で重複なし数列生成 |
| F-06 ダイス | `Math.random()` で出目計算 |
| F-09B クイズ選択肢シャッフル | `Fisher-Yates shuffle` でコード側シャッフル |

## 4. ユーザーデータの安全な管理

### 原則

- **最小限の収集**: 機能の動作に必要なデータのみ保存する
- **opt-in必須**: ユーザーが明示的に登録を要求した場合のみ永続保存する
- **削除要求への対応**: 「忘れて」「削除して」でユーザーがいつでも削除できる
- **LLMにユーザーデータを管理させない**: 記憶・検索・削除はDBで構造的に行う

### LLMに記憶管理を委ねてはいけない理由

藍(Ai)の拡張事例より: APIを複数回叩いて記憶を整理させる方式は
- APIコストが大きい
- 誤った仕様を学習するリスクがある
- 記憶の信頼性が低い

→ ユーザー固有のデータは SQLite に構造的に保存し、LLMはそれを「参照・解釈」するだけにする。

## 5. キャラクターとして断る設計

### 原則

機能の制限・拒否はルールをそのまま提示するのではなく、
担当キャラクターの口調と世界観で自然に行う。

### 具体例

#### F-10 1日1回制限を超えたとき

```
// ❌ 悪い例
「本日の占い利用上限（1回）に達しました。明日以降に再度ご利用ください。」

// ✅ 良い例（000チトセの場合）
「今日の数字はもう出たよ。また明日一緒に引こう。」

// ✅ 良い例（78ナナハの場合）
「カードは今日の答えをもう告げたよ。次は明日に。」
```

#### F-12 リマインダー3件上限を超えたとき

```
// ❌ 悪い例
「リマインダー登録数が上限（3件）を超えています。」

// ✅ 良い例（000チトセの場合）
「今3つ覚えているから、どれか一つ済んだら教えてくれるかな。
 そしたら新しいのを追加するね。」
```

#### F-07 ハラスメント L1 のとき

```
// ✅ 担当キャラが「キャラらしく」受け流す
「それは私の管轄外のデータだよ。
 ……で、本来何を話したかったんだっけ？」
```

## 6. Misskey固有機能の適切な活用

### CW（コンテンツワーニング）の活用方針

| 使うべき場面 | 使わなくていい場面 |
|------------|----------------|
| 占い・エンジェルナンバーの詳細解釈 | 100文字以内の短い応答 |
| ゲーム結果の詳細 | 挨拶・定型返答 |
| 長めのリマインド内容 | リアクション後の一言 |
| ネタバレを含む可能性があるもの | — |

### visibility 設計のまとめ

```
public   → 自発投稿 / Poll投票ノート
home     → 通常のメンション返信 / ゲーム中やり取り / 占い結果
specified → DM的なリマインド返信（フォロワー外ユーザーにも確実に届ける必要がある場合）
```

### カスタム絵文字の活用

- レスポンスに1〜2個のカスタム絵文字を添えることでAI感を和らげる
- 絵文字チェッカー（藍(Ai)の機能）は本Bot ではサーバー管理者のみの用途のため実装しない
- 未登録の絵文字名を誤って使うと文字列がそのまま表示されるため、使用する絵文字名は定数管理する

## チェックリスト（新機能追加時）

新規機能を実装・設計するときは以下を確認すること:

- [ ] 公開範囲（visibility）は適切か？ `public` が本当に必要か？
- [ ] ランダム値の生成はコード側か？LLMに任せていないか？
- [ ] ユーザーごとの利用制限があるか？DBで管理しているか？
- [ ] 制限・拒否はキャラクターの口調で行っているか？
- [ ] スケジューラーが発火する場合、1回あたりの処理件数に上限があるか？
- [ ] LLMにユーザーデータの管理を委ねていないか？DBで構造的に管理しているか？
- [ ] グローバルレートリミッタの対象に含まれているか？
