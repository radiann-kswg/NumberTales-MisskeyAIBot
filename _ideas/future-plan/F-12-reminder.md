## 概要

ユーザーがメンションで「〇時間後に〇〇を教えて」と伝えると、
指定時刻に担当キャラクターが口調に合わせてリマインドしてくれる機能。

### なぜナンバーテールズBotにとって特別な機能か

**ナンバーテールズは「主人との主従契約」によって生活をサポートする存在**という重要な世界観設定がある。
リマインダーは単なるユーティリティではなく、**キャラクターが実際にその契約を果たす場面**になる。

Fediverseでの比較:
- @remindme@mstdn.social: シンプルなリマインダーBot（コマンドライン的・無個性）
- ナンバーテールズBot: **キャラクターが「覚えておくね」と請け負い、時間になったら約束通り知らせに来る**

この「主人への奉仕」の演出が、ナンバーテールズの世界観認知につながる差別化ポイント。

## コマンドトリガー

### 登録系

```
「〇時間後に〇〇を教えて」
「〇分後に〇〇のリマインドをお願い」
「明日の〇時に〇〇を知らせてほしい」
「〇〇のことを〇時〇分に思い出させて」
「〇月〇日 〇時に〇〇をリマインドして」
「〇〇を忘れそうだから〇時間後に言って」
```

### 確認・削除系

```
「リマインダーを見せて」「何を覚えてくれてる？」「リマインダー一覧」
「〇〇のリマインダーをキャンセルして」「〇番のリマインダーを消して」
```

意図分類: `reminder-set` / `reminder-list` / `reminder-cancel`

## 時間指定の解析パターン

LLMで自然文を解析し、リマインド日時を抽出する方式が推奨。
（ルールベースでは「あさって」「来週月曜」等の相対指定が複雑になるため）

| 指定パターン | 例 | 解析結果 |
|------------|---|---------|
| 相対（分単位） | 「30分後」 | now + 30min |
| 相対（時間単位） | 「3時間後」 | now + 3h |
| 相対（日単位） | 「明日」「あさって」 | +1day/+2day |
| 絶対（今日）  | 「今日の18時」 | 今日 18:00 JST |
| 絶対（日付） | 「6月30日の10時」 | 指定日時 |
| 相対+絶対 | 「来週の月曜10時」 | 次の月曜 10:00 |

> **タイムゾーン**: JST (UTC+9) 固定。環境変数 `TZ` または設定ファイルで管理。

## ゲームフロー

### 登録時

```
[1] ユーザー: 「3時間後に薬を飲むのを教えて」

[2] LLM でリマインド内容 ("薬を飲む") と時刻 (now + 3h) を抽出

[3] セッションDBに保存
    user_id / content / remind_at / created_at / status=pending

[4] 担当キャラクターが「登録確認メッセージ」を返信:
    例(000チトセ): 「3時間後に薬の時間、覚えておくね。〇時〇分に声かけるよ。」
    例(78ナナハ): 「承知しました。〇時〇分、カードはあなたを守っているよ。」

[5] 1ユーザーの上限チェック（同時3件まで）
    → 超過時: 「今3件覚えているから、どれかキャンセルしてから登録してね」
```

### リマインド時（スケジューラーから起動）

```
[1] スケジューラー（1分or5分間隔）が pending のリマインダーを確認

[2] remind_at を過ぎているものを抽出

[3] 担当キャラクターの口調でリマインドメンションを生成・投稿
    例(000チトセ): 「クライアント君、薬の時間だよ。ちゃんと飲んでね。」
    例(74ナナヨ): 「時が来た。……薬を飲む時間だよ。天の意志に従って。」

[4] status を done に更新

[5] フォローアップ機能（オプション）:
    30分後に「さっきのリマインダー、ちゃんとできた？」と任意で確認
    （実装は後フェーズで検討）
```

### 一覧確認時

```
担当キャラクター: 「覚えているものを教えるね。
1. 〇時〇分 — 薬を飲む
2. 明日10時 — 〇〇の提出
今のところこの2件だよ。」
```

## セッションDB拡張

```sql
CREATE TABLE IF NOT EXISTS reminders (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id     TEXT NOT NULL,
  content     TEXT NOT NULL,       -- リマインド内容（自然文）
  remind_at   INTEGER NOT NULL,    -- Unix timestamp (UTC)
  status      TEXT NOT NULL DEFAULT 'pending',  -- 'pending' | 'done' | 'cancelled'
  created_at  INTEGER NOT NULL,
  note_id     TEXT                 -- 登録確認の返信ノートID（削除追跡用）
);

CREATE INDEX idx_reminders_user ON reminders (user_id, status);
CREATE INDEX idx_reminders_remind_at ON reminders (remind_at, status);
```

## スケジューラー実装

既存の `scheduler/index.ts` にリマインダーチェックを追加:

```typescript
// 5分間隔（または1分間隔）で pending を確認
async function checkReminders(): Promise<void> {
  const now = Date.now();
  const dueReminders = db.prepare(
    "SELECT * FROM reminders WHERE status='pending' AND remind_at <= ?"
  ).all(Math.floor(now / 1000));

  for (const reminder of dueReminders) {
    const character = getCurrentSchedulerChar(); // 現在の担当キャラ
    const message = await buildReminderMessage(character, reminder.content);
    await misskeyClient.createNote({
      text: `@${reminder.user_id} ${message}`,
      visibility: 'specified'  // DMまたは指定ユーザー送信
    });
    db.prepare("UPDATE reminders SET status='done' WHERE id=?").run(reminder.id);
  }
}
```

## LLM プロンプト設計

### 登録確認メッセージ

```
システムプロンプト: [担当キャラクターの個性・口調]
ユーザーメッセージ: 
  リマインドを登録しました。
  内容: {content}
  時刻: {remind_at_formatted}
  
  ユーザーへの登録確認メッセージを30文字以内で生成してください。
  キャラクターとして自然に、「〇時〇分に声をかける」ことを伝えてください。
```

### リマインド本文

```
システムプロンプト: [担当キャラクターの個性・口調]
ユーザーメッセージ:
  リマインドの時間になりました。
  内容: {content}
  
  ユーザーへのリマインドメッセージを40文字以内で生成してください。
  「主人/クライアント」への奉仕として、キャラクターらしく知らせてください。
```

## 制約・安全設計

| 項目 | 設定値 | 理由 |
|-----|-------|------|
| 同時登録上限 | 1ユーザー3件 | DB肥大化防止 |
| 最短リマインド時間 | 5分後以上 | スケジューラー精度との兼ね合い |
| 最長リマインド時間 | 30日以内 | DB保持期限・現実的な用途 |
| スケジューラー確認間隔 | 5分 | リマインドのズレ上限5分を許容 |
| 期限切れ自動削除 | 完了後7日 | DBクリーンアップ |

## 実装ステップ（着手時に詳細化）

1. **DB拡張**: `storage/session.ts` に `reminders` テーブルを追加
2. **意図分類**: `classifyIntent()` に `reminder-set` / `reminder-list` / `reminder-cancel` を追加
3. **時間解析**: LLM でリマインド日時・内容を抽出する関数を実装
4. **メンションハンドラ**: `mention.ts` に各 intent の処理を追加
5. **スケジューラー拡張**: `scheduler/index.ts` に5分間隔のリマインダーチェックを追加
6. **LLMメッセージ生成**: 登録確認・リマインド本文の生成関数を実装
7. **動作確認**: 各キャラクターの口調が正しく反映されているか、リマインドが時間通りに届くか確認
