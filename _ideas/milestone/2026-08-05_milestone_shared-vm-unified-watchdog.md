# Milestone: 共用 Spot VM 向け統合ウォッチドッグ再設計

> 起票日: 2026-08-05
> ステータス: 未着手 ⏳（設計のみ。実装は後日）
> 背景: 2026-08-05 のインフラ統合（GCP 料金軽減）による VM 移設
> 関連: [completed/2026-07-04_milestone_auto-recovery.md](./completed/2026-07-04_milestone_auto-recovery.md)（既存3層ウォッチドッグ）
> ／ [tools/gce-watchdog/](../../tools/gce-watchdog/) ／ [docs/deployment.md](../../docs/deployment.md)

## 背景

2026-08-05 のインフラ統合で、Bot の稼働環境が次のように変わった。

| 観点 | 旧 | 新 |
| ---- | -- | -- |
| インスタンス | `misskey-bots-group-numbertales`（専有） | `misskey-bots-unified`（**他 Bot と共用**） |
| プロビジョニング | 通常 VM・`automaticRestart=True` | **Spot**・`automaticRestart` 有効化不可 |
| 同居プロセス | 本 Bot のみ | 本 Bot（pm2）＋ `aphrnts-100-bot.service` ＋ `ai_bot.service`（systemd 直管理） |

既存のレイヤー3（GCE 外部ウォッチドッグ）は**専有 VM を前提に設計されている**ため、
この変化で2つの前提が崩れた。

---

## 解決したい課題

### 課題1: `reset()` が同居 Bot を巻き添えにする（共用化による新規リスク）

現行実装（[`tools/gce-watchdog/index.js`](../../tools/gce-watchdog/index.js)）は
「TCP:22 が3回とも無応答」かつ「インスタンスが `RUNNING`」で `instances.reset()` を撃つ。
これは **VM のハードリセット**なので、同居する別 Bot も道連れで強制再起動される。

本 Bot 単体の障害はレイヤー1（pm2 `autorestart`）・レイヤー2（VM 内ウォッチドッグ）が拾うため、
レイヤー3 が発火するのは本来 VM 全体の異常時に限られる。とはいえ現行の判定材料は
**TCP:22 の死活のみ**で、「本当に VM 全体が死んでいるのか」「経路側の一時障害なのか」を
区別できていない。共用環境では誤検知1回のコストが跳ね上がる。

### 課題2: `automaticRestart` が失効し、レイヤー3 が単一障害点になった

Spot では `automaticRestart` を有効化できない（`False` 固定・`onHostMaintenance=TERMINATE`）。
旧構成で「3c ホスト障害・メンテナンス」を担っていた GCE 側の自動再起動が使えないため、
**プリエンプションからの復帰はレイヤー3 の `start()` 経路だけが担う**。
ここが止まると Bot は落ちたまま復帰しない。

加えて、Spot のプリエンプションは**予告なく起こる通常運転**であり、旧構成での
「VM 停止＝異常事態」という前提はもう成立しない。異常検知とプリエンプションを
同じ扱いにしていると、ログが警告で埋まって本当の異常が埋もれる。

### 課題3: ウォッチドッグの所有者が曖昧（将来リスク）

現在 VM を監視する外部ウォッチドッグは本リポジトリの
`numbertales-gce-watchdog` **1つだけ**（2026-08-05 に全リージョンを確認済み）。
しかし同居 Bot 側のリポジトリが同種の仕組みを導入すると、**独立したクールダウンを持つ
複数のウォッチドッグが同じ VM に `reset` を撃ち合う**状態になり得る。
共用 VM である以上、レイヤー3 の所有権をどこか1つに定める必要がある。

---

## 方針

**「Bot 単位の復旧は各 Bot が持ち、VM 単位の復旧は共用の1つに集約する」**

責務を明確に分離する。

| レイヤー | 対象 | 担当 | 巻き添えの有無 |
| -------- | ---- | ---- | -------------- |
| 1 | プロセス | pm2 `autorestart`（各 Bot が個別に持つ） | なし |
| 2 | Bot の応答性 | VM 内ウォッチドッグ（各 Bot が個別に持つ） | なし |
| 3 | **VM 全体** | **共用ウォッチドッグ 1 つ**（所有者を明示） | **あり（設計で最小化する）** |

---

## 実装計画

### Phase 1: 共用前提の安全化（最小・優先）

`reset()` の誤爆コストを下げることに絞る。既存構成のまま実装できる。

- [ ] **`reset()` の発火条件を厳格化する**
      - 連続 N 回（例: 2 回＝10分間）の判定サイクルで無応答が続いた場合のみ発火させる
        （現行は1サイクル内3回リトライで即断）
      - 直前にプリエンプション履歴（`compute.instances.preempted`）がある場合は
        `reset` ではなく `start` 相当の扱いにフォールバックする
- [ ] **`RESET_ENABLED` 環境変数を追加**し、既定を「`start` のみ有効・`reset` は無効」にする
      （プリエンプション復帰という最頻ケースは `start` だけで足りるため、
      危険な操作をオプトインに落とす）
- [ ] **`reset` 実行時のログに「同居 Bot も再起動される」ことを構造化フィールドで明示**し、
      巻き添え対象を追跡可能にする
- [ ] プリエンプション由来の `start` は `warn` ではなく `info` 相当で記録し、
      異常系のログと混ざらないようにする

### Phase 2: 統合ウォッチドッグ化

- [ ] 監視対象を**配列設定**にする（`WATCH_TARGETS`: インスタンス名・IP・所有リポジトリ）
- [ ] レイヤー3 の**所有権をどのリポジトリが持つかを決めて明文化**する
      （本リポジトリが持つなら、同居 Bot 側には「外部ウォッチドッグを別途立てない」ことを共有）
- [ ] 同居 Bot の生死も併せて記録し、`reset` 判断の材料にする
      （VM 全体の異常なら全 Bot が無応答のはず。1つだけ無応答ならレイヤー2 の領分）
- [ ] 復旧アクション実行時に所有者へ通知する経路を用意する（Misskey 投稿 or ログ集約）

### Phase 3: プリエンプションの事前ハンドリング

- [ ] **Spot のプリエンプション予告を活用する。** GCE は停止の約30秒前に ACPI シャットダウン
      シグナルを送り、メタデータサーバの `instance/preempted` が `TRUE` になる。
      これを shutdown script で受けて **pm2 の graceful stop** を行い、
      SQLite（セッション・タスク・信頼度）の書き込み中断を避ける
- [ ] 予告を受けた時点でハートビートに「計画停止」フラグを立て、
      VM 内ウォッチドッグとレイヤー3 が異常と誤認しないようにする
- [ ] 復旧通知（[`features/recovery-notice.ts`](../../src/features/recovery-notice.ts)）が
      プリエンプション由来の短時間停止で過剰に発火しないか、閾値（現行30分）を実績で確認する

---

## 受け入れ条件

- [ ] プリエンプション → 自動復帰の一連が、`reset` を一度も撃たずに完了すること
- [ ] `reset` が発火する条件が「VM 全体の異常」に限定され、判断材料がログから追えること
- [ ] 同居 Bot を巻き添えにする操作が、設定で明示的に有効化しない限り走らないこと
- [ ] レイヤー3 の所有リポジトリがドキュメント上で一意に定まっていること

---

## 検証方法

**⚠️ 共用 VM での障害注入は同居 Bot に影響する。実施前に必ず所有者の合意を取ること。**

- ドライラン: 関数をローカル実行し、`TERMINATED` / `RUNNING`＋無応答 の各分岐が
  期待どおりのアクションを返すか確認する
- プリエンプション実測: `gcloud compute operations list` で
  `compute.instances.preempted` の発生日時と、Bot の復帰までの実所要時間を突き合わせる
- 障害注入（合意が取れた場合のみ・低トラフィック時間帯）: VM を手動停止し、
  レイヤー3 が `start()` で復帰させ、pm2 経由で Bot まで戻ることを確認する
