## 前提機能 A: キャラクタープロンプト個性化強化

### 目的

各個体の「得意分野・専門性」を `buildCharacterSystemPrompt()` の出力に反映し、
担当キャラクターごとに個性ある応答・占い・相談対応が自然にできるようにする。

### 使用する DB フィールド

| フィールド        | 用途                     | 非公開時の扱い              |
| ----------------- | ------------------------ | --------------------------- |
| `Hobby`           | 趣味・得意テーマ         | 空文字でスキップ            |
| `SpecialSkill`    | 特技                     | 空文字でスキップ            |
| `Favor`           | 好きなもの（補完情報）   | 空文字でスキップ            |
| `NumerospecAbout` | ヌメロジー上の役割・特性 | `hideText` 付きの場合は省略 |

### タスク詳細

#### A-1: `CharacterRecord` 型の拡張

- `src/bot/character/loader.ts` の `CharacterRecord` インターフェースに
  `Hobby`・`SpecialSkill`・`Favor`・`NumerospecAbout` フィールドを追加
- `NumerospecAbout` は `string | { hideText: string }` の Union 型として定義
- `Hobby` / `SpecialSkill` / `Favor` も同様に hideText パターンに対応する

#### A-2: `buildCharacterSystemPrompt()` への専門性セクション追加

- `src/bot/character/prompt-builder.ts` を更新
- 既存のキャラクター性格・口調セクションの後に「得意なこと・専門性」段落を追記
- 非公開フィールドは出力から除外するヘルパー `resolveTextField()` を実装する
- プロンプト例（追記イメージ）:
  ```
  【このキャラクターの得意なこと・専門性】
  趣味: タロットカード
  特技: アドリブ祝辞
  好きなもの: トランプ、タロットカード
  ヌメロジー上の特性: 経験・報酬を反省から生む
  ```

#### A-3: 型チェック・動作確認

- `npm run typecheck` でエラーゼロを確認
- fallback キャラクター（000(チトセ)）でも問題なく動作することを確認

## 前提機能 B: 週次担当キャラクター選出

### 目的

現状 000(チトセ) 固定の F-02 自発投稿担当を、
Misskey の Poll（投票）ノートを用いて週次でローテーションさせる仕組みを構築する。

### 仕様

| 項目            | 内容                                                                     |
| --------------- | ------------------------------------------------------------------------ |
| 周期            | 週1回（日曜22時）に候補3名の Poll ノートを投稿、日曜23:59 に集計         |
| 候補者選出      | `Progress: "released"` のキャラクターからランダム3名を選出               |
| 決定方式        | 最多票のキャラクターを翌週担当として確定                                 |
| 票ゼロ / 同票時 | 候補3名から抽選（`Math.random()` または crypto.randomInt）で自動決定     |
| 担当就任投稿    | 月曜7時に担当キャラクターとして就任の一言（LLM 生成・50 文字以内）を投稿 |
| デフォルト担当  | Bot 起動直後・設定未定時は 000(チトセ) が担当                            |
| 状態の永続化    | 現在の担当キャラクター番号を SQLite の `bot_state` テーブルに保存        |

### タスク詳細

#### B-1: `bot_state` テーブルの追加

- `src/storage/session.ts`（または新規 `src/storage/bot-state.ts`）に
  `bot_state` テーブルを追加
  ```sql
  CREATE TABLE IF NOT EXISTS bot_state (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL,
    updated_at INTEGER NOT NULL
  );
  ```
- `getState(key)` / `setState(key, value)` のユーティリティを実装
- `current_scheduler_char` キーに担当キャラクターの番号（文字列）を保存する

#### B-2: Poll ノートの投稿処理

- `src/bot/scheduler/` 配下に `weekly-poll.ts` を新規作成
- 日曜22時に発火するスロットを `scheduler/index.ts` に追加
- 候補3名の選出ロジック（`released` キャラクターから重複なくランダム抽出）を実装
- `misskeyClient.createPollNote()` で投票ノートを投稿（misskey-js の Poll API を使用）
- 投稿した Poll のノート ID を `bot_state` に保存（集計時に使用）

#### B-3: 集計・担当確定処理

- 日曜23:59 に発火する集計スロットを追加
- B-2 で保存した Poll ノート ID を取得し、`notes/show` API で票数を確認
- 最多票または抽選で担当キャラクターを確定し、`bot_state` に保存
- 月曜7時の自発投稿スロットで就任メッセージ（LLM 生成）を投稿

#### B-4: F-02 スケジューラーへの担当キャラクター連携

- `scheduler/index.ts` の自発投稿処理で `bot_state` から現在の担当キャラクターを取得
- 取得したキャラクター番号のシステムプロンプトを使って投稿文を LLM 生成
- 担当キャラクターが未設定の場合は 000(チトせ) の固定プロンプトにフォールバック

## 機能③: ハラスメント仲介（F-07）

### 目的

不適切・ハラスメント的なメンションに対して、担当キャラクターがパーソナリティを保ちながら
受け流し、必要に応じて 000(チトセ) または 10(ミツル) が仲介に入る仕組みを実装する。

### 10(ミツル) が仲介役である設定上の根拠

- `SpecialSkill`: 護身術
- `Unlike`: ヒューマノイドの暴走
- `Backgrounds`: 「10(ツナイ)[ディケ]」の暴走事件・退役を受けて誕生した経緯
- 公式小説（93(クミ)編 第2話「再挑戦」）: 多くのインシデントを俯瞰・記録し、
  ハラスメント・暴走場面で「止める・制止する」役割を担った描写あり

### ハラスメントレベルの分類

| レベル | 判定基準                                               | 対応                                               |
| ------ | ------------------------------------------------------ | -------------------------------------------------- |
| L1     | 軽度の不躾な要求（プライベート情報要求・軽い挑発など） | 担当キャラクターがそのまま「キャラらしく」受け流す |
| L2     | 繰り返し・エスカレートする不適切要求                   | 000(チトセ) が「設計上の制約」として介入           |
| L3     | 明らかなハラスメント・威圧・暴言レベルの言動           | 10(ミツル) が毅然と制止し、担当キャラクターを守る  |

> ⚠️ 10(ミツル) のキャラクタープロンプト・口調例・L3 返答テンプレートはクライアントから別途提供を受ける。

### タスク詳細

#### C-1: ハラスメント検知ロジックの追加

- `src/bot/classifier/intent.ts` に `harassment` インテントを追加
  - L1/L2/L3 の分類は `harassmentLevel: 1 | 2 | 3` として `ClassificationResult` に追加
- ルールベース検出（暴言・侮辱キーワード正規表現）で L1 / L2 を判定
- 判定が難しいケースは LLM による補助判定（`classifyHarassmentLevel()` ヘルパー）を設ける
- LLM 判定は誤検知リスクがあるため、ルールベース後段の補助として位置づける

#### C-2: `ClassificationResult` 型の拡張

- `intent.ts` の `ClassificationResult` に `harassmentLevel?: 1 | 2 | 3` を追加
- 既存の呼び出し側（`mention.ts`）が型エラーになっていないか `npm run typecheck` で確認

#### C-3: `mention.ts` への仲介ロジック追加

- `handleMention()` 内で `intent === 'harassment'` の分岐を追加
- L1: 担当キャラクターのシステムプロンプトで「受け流し」指示を追加した上で LLM 生成
- L2: 000(チトせ) のシステムプロンプトに切り替えて介入メッセージを LLM 生成
- L3: 10(ミツル) のキャラクタープロンプトを使って制止メッセージを LLM 生成
  （プロンプト確定前は 000(チトせ) でフォールバック）

#### C-4: L1 受け流し用プロンプト指示の追加

- `buildCharacterSystemPrompt()` の出力末尾に以下の共通指示を追記:
  ```
  【不適切な要求への対応方針】
  プライベート情報・不適切な要求を受けた場合は、このキャラクターのパーソナリティを
  保ちながら自然に断り、本来の会話・話題へ誘導すること。
  感情的に反応したり、場を壊すような返答は避けること。
  ```

#### C-5: 動作確認

- L1・L2・L3 それぞれのシナリオで期待通りの仲介が動作するかテスト
- 誤検知（通常の発言がハラスメントと判定される）がないか確認

## 実装順序（推奨）

```
Step 1: 前提 A（A-1 → A-2 → A-3）    ← 最初に完成させると C-1～C-4 の品質も上がる
Step 2: 機能③（C-1 → C-2 → C-3 → C-4 → C-5）
Step 3: 前提 B（B-1 → B-2 → B-3 → B-4）
```

A と C は同一セッション内で完結できる規模。B は Misskey Poll API の動作確認が必要なため
別セッションで取り組むのが現実的。
